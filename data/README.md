## 2. Known limitations (R049)

1. **Synthetic origin.** Every row comes from the PaySim simulator, not from real customers. Behaviour is generated by the simulator's rules, so patterns can be cleaner than in real data.
2. **Generalisation risk.** A model trained here learns the simulator; its scores on PaySim are likely to overestimate performance on real transactions of any bank, including Northstar's.
3. **Balance fields carry simulator artefacts that look "too good".** Among TRANSFER and CASH_OUT rows, "amount = whole origin balance" holds for 97.8205 % of frauds and for 1 legitimate row only; an origin balance error above one cent appears in 90.4730 % of legitimate rows against 0.5479 % of frauds (nb02 R071). The derived features `error_balance_orig` and `error_balance_dest` (J3, I36) capture these artefacts.
4. **Time artefact.** The number of frauds per step is almost constant (median 10.0 per step, Spearman with volume 0.18) while volume follows a day/night cycle, so the fraud rate per simulated hour ranges from 0.0528 % to 22.3035 %; in 320 steps every transaction is a fraud (nb02 R069). The feature `hour_of_day` (I36) partly learns this injection rhythm.
5. **Fraud only in two transaction types.** All frauds are TRANSFER (4097) or CASH_OUT (4116); PAYMENT, CASH_IN and DEBIT have 0 (nb02 R068). A fraud scenario on another type would not be learned.
6. **`isFlaggedFraud` is a weak simulator rule.** It flags 16 rows, all frauds and all TRANSFER, i.e. 0.19 % of frauds (nb02 R071). It is excluded from the predictors (brief §4.2, I36).
7. **Merchant balances are not recorded.** Recipients whose identifier starts with `M` (2151495 rows) have both destination balances at 0 in 100.0000 % of rows, and 0 frauds (nb02 R071): a 0 balance does not mean an empty account.
8. **Inconsistent origin balances.** 4,079,079 rows (64.11 %) have an amount above the origin balance before the transaction (nb02 R072).
9. **Apparent cap on fraud amounts.** The largest fraud amount is 10,000,000.00 and 287 frauds sit exactly at this value (nb02 R072). This looks like a simulator cap (hypothesis, not checked in the source documentation).
10. **Short simulated period.** 743 steps (one step = one hour per the dataset description), i.e. about one simulated month (nb02 R062, R069); no seasonality beyond the daily cycle can be studied.
11. **The split mixes simulated time.** The J3 split is stratified and random (I34); the volume changes strongly across steps (nb02 R069) and the brief §4.1 notes that a random split across steps can leak future behaviour. Question open for the founder (no change made).
12. **Fairness cannot be measured.** There is no customer attribute (age, gender, region…), only synthetic identifiers; fairness across groups of people cannot be assessed on this dataset.

## 4. Missing values (R081)

**Finding:** 0 missing values in each of the 11 columns, 0 in total (nb02 R063).
**Rule:** no imputation is needed and none is applied. The existing contract stays the rule: `validate_frame` (`src/data/schema.py`) refuses a missing target; a missing feature value is not refused at load time. If another copy of the file contained missing values, nb02 R063 would count them and the founder would decide the rule.

## 5. Duplicates (R082)

**Definitions (written before counting, nb02 R064):**
- D1 — the whole row (11 columns) is identical to an earlier row;
- D2 — same event: same `step`, `type`, `amount`, `nameOrig` and `nameDest`, even if balances or the label differ;
- D2 with contradictory labels — a D2 group whose rows do not all have the same `isFraud`.

**Counts:** D1 = 0, D2 = 0, D2 groups with contradictory labels = 0 (nb02 R064).
**Decision:** no row removed. Context (not duplicates): 18,611 rows have an `nameOrig` that appears more than once; 2.34 rows per `nameDest` on average (nb02 R064).
